FLOODGUARD BD — OFFLINE GLOFAS DATA BUILD / RENDER

BUILD
-----
pip install -r requirements.txt

START
-----
gunicorn --workers 1 --threads 1 --timeout 120 --bind 0.0.0.0:$PORT app:app

REQUIRED ENVIRONMENT
--------------------
SECRET_KEY=<long random value>

OPTIONAL
--------
GEMINI_API_KEY=<optional Copilot provider key>
EMAIL_SCRIPT_URL=<optional HTTP email webhook>
VAPID_PUBLIC_KEY=<optional browser push>
VAPID_PRIVATE_KEY=<optional browser push>
VAPID_CLAIMS_EMAIL=<mailto address used for VAPID claims>
ENABLE_BACKGROUND_ALERTS=false

DATA
----
The website does NOT call Copernicus/GloFAS at runtime.
Add Gemini's processed dataset:
    data/glofas_processed.csv

The CSV contract is documented in DATASET_SCHEMA.md.

MODEL
-----
Optional but recommended before competition deployment:
    pip install -r requirements-train.txt
    python scripts/train_model.py

This creates:
    models/floodguard_model.joblib

Without the model file, the website uses a clearly labelled transparent persistence/trend baseline derived only from the local GloFAS archive. It must not be described as ML.

SOURCE / SCIENTIFIC DEFINITIONS
-------------------------------
GloFAS historical data is gridded modelled hydrology, not a Bangladesh gauge observation. The main variable is average river discharge in m³/s.

The six FloodGuard zones are GloFAS target coordinates / nearest valid river-grid cells, not gauge stations.

FloodGuard's risk signal is a historical percentile position, not an official flood probability and not a Bangladesh government warning threshold.

RAW DATA
--------
Do not commit large raw NetCDF/GRIB archives to the web repository. Keep them archived separately. Commit the compact processed six-zone CSV and provenance report.

RENDER NOTE
-----------
The runtime is deliberately API-independent so a third-party data outage does not break the hydrological layer. Render's ephemeral filesystem means the committed dataset is the durable source for the deployed app.
